# 뭉실 재설계 및 개발 준비 계획

기준일: 2026-10-23 (Asia/Seoul) · 상태: 설계 착수안 v0.1

개발 기준: `codex/beta-core`. 입력 문서는 [요구사항 분석서](TODOSNS_Requirements_v0.1.pdf)와 [RFP](TODOSNS_RFP_v0.1.pdf) v0.1이다. 두 PDF의 제안·미정 항목을 확정 요구사항으로 바꾸지 않는다.

## 1. 유지할 목적과 설계 경계

| 구분 | 계획 |
| --- | --- |
| 제품 중심 | 작은 실천을 완료하고, 선택적으로 게시하며, 다른 사람의 실천을 내 행동으로 이어간다. |
| 대표 순환 | 할 일 생성 → 완료 → 게시 → 응원 → 가져오기 → 재완료 |
| 개인 사용 | 소셜 활동 없이도 생성·완료·기록 조회가 가능한 흐름을 우선 설계한다. |
| 기존 자산 | 현재 API·데이터·웹·네이티브 Android를 재사용 후보로 조사한다. 전면 재작성이나 특정 기술 교체를 미리 결정하지 않는다. |
| 기존 규칙 | 새 정책을 합의하기 전까지 기존 접근권한·차단·파기·보안 규칙을 유지한다. 재설계 초안은 기존 제품 규칙을 자동 폐기하지 않는다. |
| 플랫폼 | 사용자가 Android 우선을 선택했다. Kotlin/Compose 네이티브 Android를 첫 구현·검증 대상으로 두고, 공통 API·웹 호환성은 보존한다. 웹을 주 화면 대체물로 사용하지 않는다. |
| 현재 작업 | 계획·정책 결정표·검증 기준·개발 기준선 준비. 승인되지 않은 화면 재작성·DB migration·운영 배포는 범위에 포함하지 않는다. |

## 2. 단계별 산출물과 종료 조건

기간은 플랫폼·MVP 범위 합의 뒤 산정한다. 아래는 일정 확정값이 아닌 의존 순서다.

| 단계 | 수행 내용 | 산출물 | 종료 조건 | 선행 |
| --- | --- | --- | --- | --- |
| S0 개발 기준선 | 최신 소스·의존성·실행 도구·기존 검사 확인 | 개발 준비 현황, 실패/미검증 목록 | 현재 버전의 실행 결과와 환경 제약을 구분 | 없음 |
| S1 사용자·범위 | 대표 사용자와 이용 상황, 핵심/확장/제외 범위 정리 | 사용자 시나리오, MVP 범위표, 결정 로그 | 최초 플랫폼·핵심 흐름·공개 정책 합의 | S0와 병행 |
| S2 흐름·UX | Android 정보 구조·내비게이션, 화면 이동, 주요 행동과 상태 정의 | 화면 목록, 흐름도, 와이어프레임, 상태표 | 생성→완료→게시→가져오기를 정상/실패 흐름으로 설명 가능 | S1 |
| S3 계약·데이터 | 도메인 책임, API 계약, 권한, 공개 범위·파기 영향 | 계약 변경표, 권한표, 데이터 모델, ADR | 변경 호환성·보존/파기·테스트 방식 검토 | S1, S2 초안 |
| S4 구현 계획 | 기능별 작업 분해, 순서, 회귀 범위·검수 연결 | 구현 백로그, 요구사항 추적표 | 각 작업의 완료 조건·의존성·검증 방법 존재 | S2, S3 |
| S5 기능 구현 | Android 기능 단위로 구현하고 공통 API·계약·검사를 함께 반영 | 기능별 변경과 실행 증거 | 해당 요구의 정상·권한·실패 검사 통과 | S4 |
| S6 통합·인계 | 실제 합성 DB/스토리지·브라우저·대상 플랫폼 검사 | 검증 보고서, 미완료 목록, 배포/복구안 | 실제 통과·실패·미검증을 분리해 출시 판단 가능 | S5 |

## 3. 첫 출시 후보와 구현 순서

| 묶음 | 요구사항 | 설계·구현 후보 | 완료 조건 |
| --- | --- | --- | --- |
| V1 개인 실천 | F-01~05, F-13 | 로그인·첫 사용 → 할 일 생성·수정 → 날짜 조회 → 완료·취소 → 기록 | 새로고침 후 보존, 소유권 거부, 실패 시 입력 유지·상태 복원 |
| V2 선택적 게시 | F-08~09 | 완료 항목 선택 → 게시 내용·공개 범위 확인 → 피드 조회 | 비공개/차단 콘텐츠 접근 거부, 삭제·완료 취소 시 의미 일관성 |
| V3 응원·가져오기 | F-10, F-12 | 응원·취소 → 실천 미리보기·일정 조정 → 내 TODO 저장·완료 | 중복 요청 처리, 원본 권한·출처, 가져온 항목 소유권 검증 |
| V4 공개 안전 | F-18~20, N-05~07 | 신고·차단 → 운영 조치 → 탈퇴·파기 | 본인/타인/운영자 권한과 차단·탈퇴 효과 확인 |
| 확장 검토 | F-06~07, F-11, F-14~17 | 반복·그룹/분류·댓글·팔로우·알림·챌린지·채팅 | 핵심 검증·범위 합의 뒤 별도 우선순위 결정 |

V4는 공개 출시의 선행 조건이다. 순서가 뒤라는 이유로 안전 기능 없이 외부에 출시하지 않는다. 확장 후보로 분류한 기존 기능을 삭제·비활성화한다는 뜻이 아니다.

## 4. 설계할 화면과 상태

| 흐름 | 화면·행동 후보 | 반드시 다룰 상태 | 정책 의존 |
| --- | --- | --- | --- |
| 첫 사용 | 로그인·가입·첫 실천 안내 | 검증 오류, 메일 발송 실패, 중복 제출, 세션 만료 | P-02 |
| 개인 실천 | 오늘/일정, 생성·편집, 완료·취소, 개인 기록 | 빈 목록, 조회 실패, 저장 중, 오프라인, 중복·늦은 응답 | P-07 |
| 게시·탐색 | 게시 초안·공개 범위, 피드·상세 | 미디어 미완료, 공개 철회, 권한 상실, 더 보기 실패 | P-03~06 |
| 가져오기 | 원본 미리보기, 일정 조정, 저장 결과 | 원본 삭제·비공개·차단, 반복 규칙 차이, 중복 저장 | P-05/07 |
| 안전·종료 | 신고·차단, 탈퇴 확인·결과, 운영 조치 | 역할 부족, 기존 대화/복제본 처리, 파기 실패·재시도 | P-10 |

기존 5탭·공통 Sheet·키보드·접근성 계약은 현행 구현의 기준이다. 새 정보 구조와 충돌하면 설계안에서 대안을 제시해 합의하며, 기존 화면 규칙을 조용히 변경하지 않는다.

## 5. API·데이터 설계 원칙

| 항목 | 준비 방향 |
| --- | --- |
| 재사용 경계 | 인증/세션, TODO/반복/그룹, 게시/피드, 미디어, 안전/파기를 각각 조사한다. |
| 응집도 | `MungsilService`의 기존 책임을 확인하고 변경 기능이 요구하는 경우에만 경계를 나눈다. 설계 준비를 이유로 일괄 리팩터링하지 않는다. |
| 공유 계약 | `packages/contracts`에 요청·응답·오류·커서·권한 의미를 정리한 뒤 클라이언트를 연결한다. |
| 상태 모델 | 예정/완료와 게시 여부를 구분한다. 완료 취소와 게시물 처리 관계는 P-04 결정 뒤 확정한다. |
| 재시도 | 낙관적 실패 복구와 요청 키·중복 처리를 함께 설계한다. 서버 권한을 UI 표시로 대체하지 않는다. |
| 데이터 변경 | 기존 FK/PK/UNIQUE/CHECK 및 runtime/migrator/backup 경계를 유지한다. migration은 영향·복구안을 검토한 별도 작업으로 수행한다. |
| 전환 | 기존 계정·콘텐츠·Android 계약 영향을 평가한다. 운영 데이터 복사·삭제와 호환성 파괴는 자동 진행하지 않는다. |

## 6. Android 우선 개발 준비

- Kotlin/Compose 네이티브를 유지하고 첫 구현 대상으로 삼는다. 웹은 기존 서비스 회귀·공통 계약 호환성을 확인하는 대상이다.
- 현재 API를 재사용하는 방향으로 설계하되, Android 흐름에 필요한 계약 변경만 별도로 검토한다.
- UI 설계에는 뒤로 가기, 키보드/IME, Safe Area, 시스템 사진 선택, 접근성 이름·글자 확대, 프로세스 재생성·초안 복원을 포함한다.
- 합성 API와 공유 fixture로 단위·UI 상태를 검사한 뒤 실제 합성 DB/스토리지·소켓을 연결한다. 합성 provider와 실제 Google/FCM/기기 검증을 분리한다.
- Debug 조립·unit·lint를 먼저 확인한다. 연결 시험은 에뮬레이터/기기 준비 뒤, release 서명은 키·대상 승인과 별도 조건으로 검증한다.
- 첫 기능 묶음은 Android의 개인 실천(V1), 다음은 선택적 게시(V2)와 가져오기(V3)다.

## 8. 개발·검증 운영

- GitHub Actions 결제 제한은 알려진 운영 제약이다. 상태 반복 조사·수동 재실행·결제 제안·CI용 우회 커밋/Push를 하지 않는다.
- 필요한 검사는 현재 Codex에서 직접 수행하고, 소스 SHA·명령·환경·시각·통과/실패/skip/미검증을 기록한다.
- Android SDK·기기 부족은 Android 미검증으로 남긴다. 웹 통과를 Android 통과로 확대하지 않는다.
- 사용자 데이터·운영 DB·키·실계정·FCM 실발송을 개발 준비용 합성 검사에 사용하지 않는다.
- 사용자는 GitHub `docs/redesign`을 문서 공유 위치로 선택했다. 설계 산출물은 이 폴더에서 관리하고 의미 있는 문서 변경만 전달한다.
