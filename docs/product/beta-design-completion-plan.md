# 뭉실 베타 설계 마감 계획

## 1. 현재 제품 상태

뭉실의 제품 방향과 기술 기반은 이미 정해져 있다.

- 핵심 순환: `TODO 생성 → 완료 → 게시 → 응원·댓글 → 가져오기 → 다시 완료`
- 제품 구조: `오늘 · 탐색 · TODO · 챌린지 · 마이` 5개 탭
- 화면 기준: 360~430px 모바일 PWA, PC에서는 중앙 모바일 프레임
- 데이터 기반: PostgreSQL, Prisma, Redis, MinIO, NestJS, Next.js
- 베타 방식: 초대 코드가 있는 10~30명 규모의 폐쇄형 베타
- 디자인 방향: 성인용 감성 라이프스타일 앱인 Cloud Comfort

현재 구현은 화면 시안 수준을 넘어 실제 API와 DB에 연결되어 있다. 다만 아래 규칙과 운영 흐름은 제품 출시 전에 더 구체적으로 확정해야 한다.

## 2. 설계가 남아 있는 영역

### 2.1 가입과 인증

- 가입 성공과 인증 메일 발송 실패를 분리한다. 사용자 레코드가 만들어진 뒤 SMTP가 실패해도 가입 요청 자체를 500으로 표시하지 않는다.
- 가입 결과는 `인증 대기` 상태로 반환하고, 메일 발송 실패 시 같은 화면에서 재발송할 수 있게 한다.
- 초대 코드는 대소문자를 구분하지 않으며, 만료일·사용 횟수·비활성 상태를 운영자가 확인할 수 있게 한다.
- 이메일 인증 전 사용 가능 범위, 인증 링크 만료 후 복구 방식, 비밀번호 재설정 후 기존 세션 폐기 규칙을 확정한다.
- 학교 서버 시험 환경은 실제 SMTP와 Mailpit 중 어떤 방식인지 환경별로 명확히 분리한다.

### 2.2 TODO 핵심 순환

- TODO 상태를 `예정 · 진행 중 · 완료 · 삭제`로 정의하고 각 상태에서 가능한 행동을 고정한다.
- 완료 직후에는 게시 제안을 보여주되 게시하지 않아도 완료 기록은 유지한다.
- 완료 취소 시 이미 게시된 게시물이 있다면 게시물 처리 선택을 먼저 받는다.
- 반복 TODO의 `이번 일정만`, `이후 일정 전체`, `반복 종료`가 각각 어떤 발생분을 바꾸는지 문구와 서버 규칙을 일치시킨다.
- 가져온 TODO는 원본과 독립적으로 수정할 수 있고 원본 삭제·비공개 전환에 영향을 받지 않는다.
- 리스트 가져오기는 모든 항목을 미리 채운 작성 화면으로 연결하며 일부 항목을 제외하거나 수정할 수 있게 한다.

### 2.3 게시와 탐색

- 공개 범위를 `나만 보기 · 팔로워 · 전체 공개`로 통일하고 TODO, 리스트, 게시물에 동일한 권한 행렬을 적용한다.
- 피드의 기본 정렬은 베타 기간에는 최신순으로 고정하고 관심사 필터만 제공한다.
- 게시물의 주 행동은 `나도 할래요`, 보조 행동은 응원과 댓글로 유지한다.
- 게시물 삭제 시 TODO 완료 기록은 남기고, 미디어는 다른 기능에서 사용하지 않을 때만 정리한다.
- 차단한 사용자와 차단당한 사용자는 검색·피드·댓글·프로필·가져오기에서 서로 노출되지 않는다.

### 2.4 등급과 포인트

- 누적 뭉실력은 장기 등급, 최근 활력은 최근 활동 상태, 사용 가능 포인트는 소비 재화로 역할을 구분한다.
- TODO 완료 보상은 하루 상한을 두고 완료 취소·재완료로 중복 지급되지 않게 한다.
- 포인트 소비는 우선 커뮤니티 챌린지 생성에만 사용한다.
- 등급별 정확한 이름·경계·혜택을 베타 전에 확정한다. 베타에서는 혜택보다 칭호와 시각적 성장만 제공한다.

### 2.5 챌린지

- 핵심 순환 안정화 전에는 조회·참여·오늘 인증·참여 취소까지만 사용자 기능으로 유지한다.
- 커뮤니티 챌린지는 500포인트, 칭호 보상, 느슨한 인증으로 운영한다.
- 공식 챌린지는 운영자 생성, 명시된 보상 조건, 검수 및 지급 상태를 사용한다.
- 기간 밖 인증, 같은 날짜 중복 인증, 다른 사용자의 미디어 재사용을 서버에서 거부한다.

### 2.6 알림과 재방문

- 베타 알림은 앱 내부 알림만 제공하고 푸시 알림은 다음 단계로 미룬다.
- 알림은 응원, 댓글, 가져오기, 팔로우, 챌린지, 등급 상승으로 분류한다.
- 알림을 누르면 대상이 삭제됐거나 권한이 없을 때도 깨진 화면 대신 설명 상태를 보여준다.
- 읽음 처리는 전체 읽음뿐 아니라 개별 읽음도 지원하도록 확장한다.

### 2.7 운영과 안전

- 신고 대상, 신고 사유, 처리 상태, 제재 기준을 운영자 화면과 API에 동일하게 정의한다.
- 운영자는 사용자 정지·해제, 게시물 숨김, 신고 기각·해결, 초대 코드 발급·중지를 수행할 수 있어야 한다.
- 개인정보 처리방침과 이용약관은 현재 자리표시자이므로 베타 참여 동의, 사진 공개, 계정 삭제 정책을 포함한 실제 문안으로 교체한다.
- DM은 베타 범위에서 제외한다. 남아 있는 메시지 API와 WebSocket은 사용자 UI에 노출하지 않고 이후 유지 여부를 결정한다.

### 2.8 측정과 피드백

- 핵심 이벤트는 가입 완료, TODO 생성, 완료, 게시, 응원, 댓글, 가져오기, 가져온 TODO 완료로 제한한다.
- 개인을 직접 식별하는 본문이나 TODO 제목은 분석 이벤트에 보내지 않는다.
- 베타 성공 지표는 가입자 수보다 `가져오기 후 재완료율`, `7일 재방문`, `완료 후 게시율`을 우선한다.
- 앱 안에 간단한 피드백 진입점을 두고 화면 경로, 앱 버전, 오류 요청 ID를 함께 수집한다.

## 3. 화면 설계 마감 목록

다음 화면은 정상 상태뿐 아니라 로딩, 빈 상태, 오류, 오프라인, 권한 없음, 성공 상태까지 설계한다.

1. 가입, 이메일 인증 대기, 재발송, 로그인, 비밀번호 재설정
2. 오늘 TODO, 완료 확인, 완료 후 게시, 완료 목록의 나중 게시
3. 주간·월간 캘린더, TODO 작성·편집, 반복 일정 편집, 삭제 복구
4. 탐색 피드, 검색 결과, 게시물 상세, 댓글, 가져오기 편집
5. 챌린지 목록·상세·인증·참여 취소
6. 마이, 공개 프로필, 팔로워·팔로잉, 프로필 편집
7. 알림, 설정, 신고, 차단, 계정 탈퇴
8. 운영자 신고함, 사용자 제재, 초대 코드 관리

## 4. 다음 개발 순서

### 단계 A — 가입과 베타 진입 안정화

- SMTP 실패가 가입 전체를 실패시켜 보이지 않도록 응답 계약 수정
- 인증 대기·재발송 화면 정리
- 초대 코드 운영 API와 간단한 관리자 UI 추가
- 테스트 환경 Mailpit, 운영 환경 SMTP 설정 분리
- 가입·인증·로그인·재설정 통합 테스트 보강

완료 기준: 신규 사용자가 같은 이메일로 꼬이지 않고 `초대 코드 → 가입 → 인증 → 로그인 → 온보딩`을 끝낼 수 있다.

### 단계 B — 핵심 순환 UX 마감

- 완료 직후 게시와 나중 게시 흐름 통합
- 단일 TODO와 리스트 가져오기 편집 경험 통일
- 반복 TODO 편집·종료 문구 및 서버 동작 일치
- 게시물·댓글·응원·가져오기 실패 원복 상태 검증
- 두 사용자 실제 DB E2E를 학교 스테이징에서도 실행

완료 기준: 사용자 A의 게시부터 사용자 B가 가져온 TODO를 완료하는 과정이 막힘 없이 한 번에 통과한다.

### 단계 C — 베타 운영 도구와 품질

- 완료: 초대 코드 발급·중지, 신고 처리, 사용자 검색·정지·세션 폐기, 게시물·댓글 숨김·복구 운영 화면
- 완료: 운영 현황과 관리자 행동 감사 기록
- 구조화 로그와 요청 ID를 활용한 오류 조회 절차
- 백업 자동화와 실제 복원 점검
- 360px·390px·430px 및 모바일 키보드·접근성 수동 점검
- 핵심 이벤트 계측과 앱 내 피드백 기능

완료 기준: 운영자가 서버 셸과 DB를 직접 수정하지 않고 베타 사용자를 관리하고 장애를 추적할 수 있다.

### 단계 D — 폐쇄형 베타

- 3~5명 내부 시험 후 10~30명 초대
- 첫 3일은 가입과 데이터 유실 문제를 우선 수정
- 1주 후 핵심 지표와 피드백으로 TODO·게시·가져오기 흐름을 재조정
- 핵심 순환이 안정된 뒤 챌린지 2차와 Google 로그인을 진행

## 5. 지금 확정하는 범위

- 다음 구현은 단계 A부터 시작한다.

- 공개 피드는 최신순, 추천 알고리즘은 베타 이후로 미룬다.
