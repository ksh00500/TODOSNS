# 뭉실 초대 베타 배포·복원·롤백 런북

이 문서는 코드 저장소 기준 절차다. 운영 도메인, 서버 접근 담당자, 장애 연락처, 외부 백업 위치와 법적 보유 기간은 배포 승인 전에 실제 값으로 채워야 한다. 이 문서만으로 법률·보안 검토가 완료된 것은 아니다.

## 1. 배포 전 승인 조건

- 대상 서버가 뭉실 전용 테스트/운영 데이터베이스와 S3 버킷을 사용하는지 확인한다. 다른 프로젝트의 컨테이너·포트·볼륨을 재사용하지 않는다.
- `.env`의 도메인, SMTP, S3 버킷·리전, Caddy 이메일을 실제 값으로 설정하고 access/refresh JWT 비밀은 서로 다른 32자 이상 난수로 만든다. `.env.example`의 값은 운영에 사용하지 않는다.
- AWS 운영 API에는 장기 Access Key를 주입하지 않고, 대상 S3 버킷으로 제한한 EC2 IAM Role의 임시 자격 증명을 사용한다.
- 개인정보 처리방침·약관의 운영 주체, 연락처, 수집 항목, 보유·파기 기간과 동의 버전을 담당자가 확정한다.
- `npm ci`, `npm run lint`, `npm test`, `npm run build`, `npm audit --omit=dev`와 격리 PostgreSQL E2E를 통과시킨다.
- Docker 이미지 태그를 커밋 SHA로 고정하고 배포할 이미지의 digest를 기록한다. `latest`만으로 배포하지 않는다.
- DB와 사진의 사전 백업을 서로 같은 배포 변경 번호로 기록하고, 최근 백업의 실제 복원 점검 결과가 있어야 한다.

## 2. 사전 백업

`infra/backup.sh`는 로컬·스테이징 DB 덤프와 MinIO 데이터 보관 파일을 검사한 뒤 확정 이름으로 이동한다. AWS 운영에서는 `infra/backup-to-s3.sh`로 DB 덤프를 S3에 직접 전송한다. 사진은 운영 S3 버킷에 있으므로 버킷 보호 설정과 별도 복구 정책을 운영 요구에 맞춰 결정한다.

1. 운영 담당자가 백업 목적지의 여유 공간·접근 권한·암호화를 확인한다.
2. 배포 직전 백업을 실행하고 종료 코드가 0인지 확인한다.
3. 생성된 DB gzip의 비압축 크기가 0보다 큰지 확인하고, MinIO를 사용하는 스테이징에서는 미디어 tar도 열리는지 확인한다.
4. 백업을 서비스 서버와 다른 장애 영역의 미확정 외부 위치로 복제한다.
5. 백업 파일명, 체크섬, 커밋 SHA, DB 마이그레이션 목록과 실행자를 배포 기록에 남긴다.

## 3. 배포 순서

1. 현재 `/health/live`와 `/health/ready`, 디스크·메모리, PostgreSQL·Redis·S3 상태를 기록한다.
2. 커밋 SHA 이미지로 웹/API를 준비하되 아직 기존 트래픽을 바꾸지 않는다.
3. 마이그레이션 SQL을 검토한다. 삭제·축소·NOT NULL 추가처럼 이전 코드와 호환되지 않는 변경은 같은 배포에 넣지 않고 확장 → 코드 전환 → 후속 정리 순서로 나눈다.
4. 단일 배포 작업에서 `prisma migrate deploy`를 한 번 실행한다. API 복제본마다 동시에 실행하지 않는다.
5. 새 API의 readiness가 성공한 뒤 새 웹과 프록시를 전환한다.
6. 아래 스모크 테스트를 수행하고 모두 성공한 뒤 배포 완료로 기록한다.

## 4. 배포 후 스모크 테스트

- 비회원 공개 피드의 기본/필터/다음 페이지와 미지원 `mode`의 400 응답
- 계정 A 로그인 → TODO 생성·완료·게시 → 계정 B 응원·댓글·가져오기·완료
- A 로그아웃 뒤 B로 전환했을 때 A의 TODO·알림·사진이 캐시나 늦은 응답으로 나타나지 않음
- 채팅 참여 취소·계정 정지·토큰 만료 직후 기존 Socket이 끊기고 새 메시지/사진 URL을 받지 않음
- 10MB 초과·타인 `mediaId`·중복 사진 연결 거부, 정상 사진 업로드/처리/표시
- 인증 메일 실제 도착, 만료 링크·재사용 링크 거부, 만료 액세스 토큰 로그아웃 시 refresh 쿠키와 서버 세션 폐기
- 요청 ID가 응답과 구조화 로그에서 연결되며 5xx·메일·미디어 정리 실패 경보가 담당자에게 도착

## 5. 롤백

- 애플리케이션 결함이고 새 마이그레이션이 이전 이미지와 호환되면 기록한 이전 digest로 웹/API만 되돌린다.
- 마이그레이션이 이전 코드와 호환되지 않으면 이미지만 되돌리지 않는다. 쓰기를 차단하고 영향 범위를 확인한 뒤, 검토된 전진 수정 마이그레이션 또는 아래 복원을 선택한다.
- 비밀값 노출이 원인이면 이미지 롤백과 별개로 해당 JWT/SMTP 자격 증명을 회전하고 모든 관련 세션을 폐기한다. IAM Role 권한이 과도하거나 악용된 경우 정책을 차단하고 CloudTrail의 영향을 확인한다.
- 롤백 뒤 핵심 순환과 권한 회수 스모크 테스트를 다시 실행한다.

## 6. 격리 복원 검증

운영 데이터 위에 직접 복원하지 않는다.

1. 네트워크와 자격 증명이 운영에서 분리된 새 PostgreSQL과 복원 검증용 S3 버킷을 준비한다.
2. DB gzip을 새 DB에 복원하고 `prisma migrate status`로 스키마 상태를 확인한다.
3. 미디어 복구 정책을 사용하는 경우 복원 검증용 S3 버킷에 객체를 복원한다.
4. 임의의 실제 사용자 2명을 선택하지 말고, 사전에 기록한 복원 검증용 합성 계정으로 계정·TODO·그룹·게시물·댓글·채팅·미디어 행 수와 참조 무결성을 확인한다.
5. 서명 URL로 원본/썸네일을 읽고, 탈퇴 작성자의 공동 챌린지·대화·감사 이력이 보존되는지 확인한다.
6. 결과, 소요 시간(RTO), 복구 시점(RPO), 누락·손상 건수를 기록하고 실패하면 해당 백업을 정상으로 표시하지 않는다.

## 7. 아직 실제 값이 필요한 항목

- 운영 주체·장애/개인정보 연락처와 대응 시간
- 실제 앱 도메인, DNS/TLS 종단, S3 리전·버킷, 학교 프록시와 허용 포트
- SMTP 계정과 발신 도메인 인증, 오류 수집·디스크 경보 수신처
- 암호화된 외부 백업 위치, 백업 주기·보유 기간·복원 목표
- 개인정보·신고 증거·감사 로그·탈퇴 데이터의 법적/제품 보유 정책
