# 뭉실 운영 DB 분리·데이터 거버넌스·보안 구현 프롬프트

작성: 2026-09-08. 저장소 확인 기준: `7926379`, PostgreSQL 17 계열·Prisma 6.12.0.

이 문서는 새 작업에서 사용할 실행 지시다. 작성 시점에는 DB·제품 코드·운영 환경을 변경하지 않았다. 특정 데이터의 보관·판매에 대한 법률 검토 완료를 뜻하지 않는다.

추가 반영: 데이터 보안등급, 목적별 S3 보관·실제 파기, 연령대 일반화, **평소 월별 집계 누적 → 탈퇴 시 지체 없는 파기 → 월말 통계 검토**. 아래 내용은 구현 계획이며 운영 데이터 처리 활성화 승인은 아니다.

## 먼저 확인한 사항

### PK/FK를 없애면 보안이 좋아지는가?

일반적으로 그렇지 않다. PK는 행 식별자이고 테이블 관계는 보통 FK가 다른 테이블의 PK/UNIQUE를 참조한다. FK는 관계의 무결성을 지킨다. FK 제약만 없애고 같은 사용자 ID를 두 테이블에 남겨두면 여전히 조인 가능하고, 오히려 고아 데이터와 삭제 누락 위험이 커진다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/17/ddl-constraints.html)

올바른 구분은 다음과 같다.

- 운영 테이블: 필요한 PK/FK/UNIQUE/CHECK를 유지한다.
- 식별정보: 접근 권한과 담당 처리 경로를 제한한다.
- 가명 분석정보: 목적별 가명 키를 사용하고 재연결 정보를 별도 제한 영역에서 관리한다. 이것도 개인정보로 취급한다.
- 익명 집계 결과: 사용자 ID·안정적인 개인별 가명 키·개인으로 돌아가는 매핑을 제공하지 않는다. PK/FK 부재만으로 익명성을 인정하지 않고 결과의 재식별 위험까지 검토한다.

PostgreSQL 스키마는 이름 공간이다. 같은 계정이 모두 읽을 수 있으면 강한 격리가 아니다. 역할·GRANT·소유권·search_path를 함께 설계해야 한다. [PostgreSQL 스키마 문서](https://www.postgresql.org/docs/17/ddl-schemas.html)

### ‘최대한 보관’의 구현 기준

목표는 **명확하고 적법한 목적에 필요한 데이터 가치를 최대한 보존**하는 것이다. 미래에 팔릴 가능성만으로 모든 원문을 무기한 저장하는 것이 아니다. 최소 수집·목적 제한·파기 원칙을 지키면서, 합법적으로 유지 가능한 집계·승인된 분석 자료·필요한 증빙을 데이터별로 판단한다. [개인정보 보호법](https://law.go.kr/LSW/lsInfoP.do?lsiSeq=270351)

가명정보는 통계작성·과학적 연구 등의 특례 요건, 별도 보관·관리·기록 의무를 검토해야 한다. 상업적 목적이라는 이유만으로 일률 금지되는 것도, 판매 계약만 있으면 자유롭게 제공할 수 있는 것도 아니다. [가명정보 조문](https://law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1020398635), [개인정보위 2026년 가이드라인 개정 안내](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11928)

### Prisma 이전 주의

현재 6.12.0에서는 multiSchema의 preview 설정/호환성을 확인해야 한다. 공식 문서상 일반 제공 전환은 6.13.0이다. 또한 모델/enum의 스키마 이동은 자동 마이그레이션에서 삭제·생성으로 나올 수 있다. 단순히 `@@schema`를 붙여 자동 SQL을 운영에 적용하지 않는다. [Prisma preview 기능 이력](https://www.prisma.io/docs/orm/v6/reference/preview-features/client-preview-features), [다중 스키마 문서](https://docs.prisma.io/docs/orm/v6/prisma-schema/data-model/multi-schema)

### 이번에 확정한 처리 방향

- 보안등급은 ‘누가 어떤 경로로 접근하는가’, 보유정책은 ‘무슨 근거로 언제까지 보관하는가’로 분리한다.
- DB에서 제거한 원문을 S3에 복사하는 것은 파기가 아니다. S3는 적법한 운영 파일·백업·보존 예외·분석 결과를 목적별로 담는 저장소다.
- 이름 삭제와 연령대 변환만으로 익명정보가 되지 않는다. 다른 정보와 결합한 재식별 위험을 평가한다. [개인정보 보호법 제58조의2](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334565)
- 통계의 시간 구간은 월 단위, 내부 집계 작업은 매일을 기본안으로 한다. 탈퇴 때만 집계해 탈퇴자 중심의 표본을 만들지 않는다.
- 탈퇴 파기는 월말 집계와 독립적으로 처리한다. 미집계 자료가 있거나 분석 작업이 실패해도 파기를 미루지 않는다. 불필요해진 개인정보는 원칙적으로 지체 없이 파기해야 한다. [개인정보 보호법 제21조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900078981)
- 월말에는 검증·소수 집단 보호·결과 버전 확정을 한다. 월말 도달이나 집계 성공이 익명성 또는 외부 제공 승인으로 이어져서는 안 된다.

현재 서비스와 기존 데이터를 보존하면서 다음을 구현해라.

계획만 작성하고 끝내지 말고 가능한 로컬 구현과 합성 데이터 검증을 수행해라. 단, 운영 데이터의 이전·삭제·새 목적 분석·외부 반출은 이 요청만으로 승인된 것이 아니다. 법적/제품 정책 결정이 필요한 부분은 별도 승인을 받고, 그동안 해당 수집·보관·반출 경로를 비활성화한 채 나머지 안전한 구현을 진행해라.

### 2. 데이터 분류표와 보유 정책부터 만들어라

`docs/architecture/data-inventory-and-retention.md`를 작성하고 모델뿐 아니라 필드 단위로 필요한 분류를 해라.

각 항목에 다음을 기록한다.

- 원천 모델/필드, 데이터 주체, 민감도, 개인/가명/익명 여부.
- 수집·운영·분석·제공 각각의 구체적인 목적과 필요한 최소 필드.
- 법적 근거 후보 및 검토 상태, 동의가 근거인 경우 동의 버전·선택 여부·철회 처리.
- 보유 시작 이벤트·기한/기간 산정 근거·만료 동작·연장 승인 조건.
- 원본·가공본·캐시·검색 인덱스·로그·객체·백업·외부 복제본의 위치.
- 탈퇴/삭제/목적 종료 시 삭제·추가 가공·보존 예외와 그 근거.
- 읽기/쓰기/반출 역할, 감사 항목, 파기 테스트.

확정되지 않은 근거·보유기간을 허구의 법정 기간으로 채우지 마라. 기존 7일 탈퇴 유예, 90일 채팅 수명, 14일 백업 같은 구현값이 법적 보관 허가라고 가정하지 마라.

확정 목적 없는 신규 분석 원문 적재는 기본 비활성화한다. 그렇다고 기존 운영 데이터를 무작정 지금 삭제하지도 마라. 필요한 정책 결정과 기존 처리방침 변경을 사용자에게 명확히 알려라.

#### 데이터 보안등급과 적용 규칙

다음은 내부 보안 분류이며 법률상 ‘민감정보’ 여부와 별개다. 건강 관련 메모 등 법적 민감정보 해당 여부는 별도 필드로 검토한다.

| 등급 | 예시 | 기본 통제 |
| --- | --- | --- |
| L0 공개 가능 | 공개 승인된 게시물·프로필 항목, 반출 승인된 집계 | 승인된 API/view만 제공. 공개 범위 변경·차단·파기 정책은 계속 적용 |
| L1 개인·참여자 한정 | 비공개 TODO, 대화, 비공개 인증 사진 | 소유자·참여자·차단 관계를 요청마다 확인 |
| L2 식별·인증 제한 | 이메일·생년월일·비밀번호 해시·세션·목적별 연결표 | 담당 기능의 최소 DB 역할만 접근, 로그·일반 분석 반출 금지 |
| L3 운영 특별 제한 | 신고 원문·증거·조사 자료·관리자 복구 비밀 | 사유·승인·필요 시 재인증, 민감 조회 감사, 기간 제한 |

- 등급은 단순 숫자 우열에 따른 상속 권한이 아니다. L3 운영자도 모든 L1 대화나 L2 인증 정보를 자동 열람할 수 없다. 등급 × 목적 × 기능 역할 × 소유/참여 관계로 판단한다.
- 같은 테이블에 다른 민감도의 필드가 있으면 테이블 분리·제한 view·DTO allowlist 중 실제 DB 접근까지 보호되는 방식을 선택한다. 등급마다 똑같은 테이블을 복제하지 않는다.
- 공개 게시물에 연결된 비공개 원본 TODO·사진·이메일이 함께 공개되지 않게 한다. 혼합 산출물은 가장 엄격한 입력 통제를 기본 적용하고, 별도 가공·검토 후에만 낮은 등급으로 전환한다.
- 등급·처리 목적·개인정보 유형·보유정책·처리 상태는 별도 속성으로 관리한다. 모든 행에 불필요한 칼럼을 붙이기보다 공통 정책 레지스트리를 우선하고, 객체/데이터셋처럼 값이 달라지는 단위에 참조를 둔다.
- 공개 가능 등급의 S3 객체도 기본 버킷 공개를 의미하지 않는다. 서버가 승인한 제공 경로를 통해 노출한다.

### 3. 권장 스키마 경계

아래를 기본 설계안으로 사용하되 현재 규모에서 불필요한 서버/마이크로서비스 분리는 하지 마라. 경계를 바꾸면 이유를 ADR에 적어라.

| 스키마 | 역할 | 주요 후보 |
| --- | --- | --- |
| `identity` | 인증·직접 식별·연결 비밀 | AccountIdentity, Session, VerificationToken, InviteCode, MFA/복구 정보, 제한된 목적별 매핑 |
| `service` | 실제 제품 데이터 | ServiceProfile 및 기존 TODO/그룹/카테고리/피드/채팅/챌린지/미디어/포인트/알림 |
| `governance` | 처리 목적·동의·수명·반출 승인 | ProcessingPurpose, PolicyVersion, ConsentRecord, RetentionPolicy, ErasureRequest/Task, ReleaseReview |
| `security_audit` | 최소 보안·관리 증빙 | 기존 AdminAuditLog와 민감 조회/권한 변경/파기 증빙 |
| `analytics_restricted` | 승인된 목적 한정 분석 | 목적별 최소 이벤트/집계 준비 데이터, 처리 작업 이력 |
| `analytics_release` | 검토된 집계 결과 | AggregateMetric, DatasetRelease, 실제 외부 제공용 승인 view |

이름은 후보이며 같은 역할의 기존 모델을 중복 생성하지 않는다. 거대한 `User` 모델의 인증·프로필·활동 필드를 분리하되 기존 사용자 ID와 API DTO 호환성을 최대한 보존한다. 이메일이 없다고 프로필·핸들·자유서술이 익명 데이터가 되는 것은 아니다.

처음에는 기존 User ID를 보존한 일대일 프로필/식별 테이블 분리와 명시적인 FK를 사용할 수 있다. 불필요하게 모든 PK를 새 UUID로 바꾸거나 기존 외부 링크를 깨지 마라. 랜덤 ID는 열거를 어렵게 할 뿐 권한 검사를 대체하지 않는다.

### 4. PK/FK와 가명 키 규칙

- 서비스 내부와 같은 신뢰 경계의 테이블에는 필요한 PK/FK/UNIQUE/CHECK를 유지한다.
- 모든 관계를 Cascade 또는 SetNull로 일괄 변경하지 말고 관계별 파기·공동 기록 보존 의미를 정의한다.
- FK를 없애고 동일 userId를 복제해 두는 것을 ‘비식별화’라고 부르지 마라.
- 가명 분석에 개인별 연결이 꼭 필요하면 목적/데이터셋 범위의 랜덤 subject key 또는 검토된 목적별 토큰화를 사용한다.
- 재연결 매핑은 제한된 별도 테이블/역할에서만 접근하며 원문 계정 ID가 분석 영역 전체에 퍼지지 않게 한다. 키를 매핑과 같은 권한 영역에 무방비로 두지 않는다.
- 이메일/전화번호의 단순 해시는 익명정보가 아니다. 안정적인 가명 키와 장기 행동 이력도 가명정보로 관리한다.
- `analytics_release`에는 개인의 userId, 이메일 해시, 안정적인 개별 subject key, 원본 eventId, 개인으로 돌아가는 FK/매핑을 넣지 않는다. 집계 차원·release version 등에 대한 PK/FK는 사용할 수 있다.
- FK가 없더라도 날짜·희귀 속성·소규모 챌린지 조합으로 재식별 가능한지 평가한다.
- 매핑을 없앴다는 이유만으로 남은 행 수준 이력을 익명으로 재분류하지 마라. 삭제 추적이 필요한 단계에서는 승인된 최소 매핑을 유지하고, 파기 시점에 원본/가명 행까지 처리한 후 정책대로 제거한다.

### 5. DB 권한은 실제 연결로 검증해라

권한 행렬을 작성하고 PostgreSQL role/grant SQL과 로컬 테스트 구성을 제공한다.

- 객체 소유자/마이그레이션 역할: 런타임과 분리. API가 migration 권한을 상시 갖지 않는다.
- 인증 처리 역할: identity의 필요한 테이블만 접근.
- 서비스 역할: service와 명시적 최소 identity 조회 경로만 접근.
- 정리 작업 역할: 승인된 파기 작업 수행 범위만 접근.
- 분석 적재 역할: 허용된 최소 데이터 경로와 restricted 쓰기만 접근.
- 분석가 역할: 승인된 restricted dataset/view만 접근, identity/매핑은 거부.
- 반출 역할: 승인된 release view만 SELECT. 운영 데이터 JOIN·임의 테이블 덤프 금지.
- 감사 기록: 일반 런타임의 수정/삭제는 거부하고 승인된 보존기간 정리 경로를 별도로 둔다.

SUPERUSER/BYPASSRLS/DB owner/CREATE ROLE/광범위 CREATE를 런타임에 주지 않는다. public CREATE·default privileges·안전한 search_path와 schema-qualified SQL을 검토한다. 과거 과도한 GRANT도 회수되는지 확인한다.

Prisma 모델에서 필드를 숨기는 것만으로 DB 권한이 생기지 않는다. 제한된 실제 DB 계정으로 forbidden SELECT/JOIN/DDL/DELETE가 실패하는 테스트를 작성해라. 계정 분리로 기존 nested query가 실패하면 필요한 최소 조회/Repository/Prisma client 경계를 명시적으로 조정한다.

RLS를 도입하면 connection pool/transaction별 사용자 context 초기화와 누출 방지, owner/BYPASSRLS의 우회까지 테스트한다. 전역 SET이나 사용자 입력을 그대로 SQL 정책에 넣지 마라. RLS 없이 구현한다면 객체별 서버 권한 검사와 DB role의 보호 범위를 분명히 문서화한다.

같은 API 프로세스가 모든 DB 비밀을 갖고 있으면 전체 프로세스 침해에 대한 완전 격리는 아니다. 단일 PostgreSQL 스키마 분리는 DBA나 공유 rootful Docker 관리자에 대한 경계도 아니다. 실제 격리 수준과 남은 위험을 과장하지 마라.

### 6. 데이터 보존형 다중 스키마 마이그레이션

현재 Prisma 6.12.0, prisma.config.ts, 생성 위치, Docker 빌드, 테스트의 import 경로를 확인한다. multiSchema preview 유지와 검증된 호환 버전 갱신 중 최소 위험안을 선택하고 이유를 기록한다. 무조건 최신 메이저로 바꾸지 마라.

필수 순서:

1. 기존 DB의 모델/enum/제약/index/시퀀스/view/trigger/`_prisma_migrations`와 실제 사용 SQL을 목록화한다.
2. 새 DB role과 schema 생성, 초기 권한을 준비한다.
3. 스키마 이동은 가능한 `ALTER TABLE ... SET SCHEMA`, enum type 이동 등 데이터 보존 SQL로 검토한다. 자동 diff의 DROP/CREATE를 그대로 적용하지 않는다.
4. User 분할은 expand → backfill → 검증 → 앱 전환 → 후속 contract 순으로 진행한다. 잠금·중단 시간과 dual-write가 필요하면 실패/재처리 전략까지 정의한다.
5. 기존 PK·FK·unique·인덱스·행 수·참조 무결성·필수 필드·원본/복제 연결을 전후 비교한다.
6. enum/schema annotation과 Prisma migration history, introspection drift, seed/backup/restore/raw SQL 경로를 함께 맞춘다.
7. 완전히 빈 DB의 전체 migration과 기존 스키마 합성 데이터가 있는 DB의 업그레이드 양쪽을 테스트한다.
8. 되돌리기 가능한 단계와 불가능한 contract 단계를 구분한다. 암호화 백업과 격리 복원 없이 운영 적용하지 않는다.

운영에 `db push`, `migrate reset`, 기존 적용 migration 수정, 테이블 drop/recreate로 데이터 재생성, FK 무효화 후 방치는 금지한다. 원격 실제 DB migration은 별도 승인 대상이다. 로컬에서도 뭉실 전용 합성 DB인지 확인한 뒤 실행한다.

### 7. 삭제와 보관을 별도 워크플로로 구현

‘화면에서 숨김’, ‘되돌릴 수 있는 소프트 삭제’, ‘탈퇴’, ‘동의 철회’, ‘보유기간 종료’를 구분한다. `archive_deleted_users`처럼 삭제된 원문 전체를 영구 복사하는 테이블은 만들지 마라.

기본 동작:

- 탈퇴 요청 시 접근 토큰/세션/소켓을 차단하고 신규 분석 수집과 신규 공개 제공을 중단한다.
- 승인된 정책 버전에 따라 ErasureRequest/Task를 생성한다. 요청 ID, 정책 버전, 처리 단계, 기한, 재시도/오류, 완료 증거를 최소한으로 관리한다.
- DB·미디어 원본/파생·메시지 수정 이력·캐시·검색·분석 중간 데이터·pending outbox까지 범위를 추적한다.
- 개인 TODO/메모/채팅/사진 원문을 ‘이름을 지웠다’는 이유로 보관하지 않는다. 공동 기록 유지가 필요하면 본문 내 식별정보까지 고려한 정책을 승인받는다.
- 완성된 익명 집계와 개인별 가명 분석 행을 구분한다. 개인별 가명 행은 별도 적법 근거와 목적별 기간이 없으면 보관하지 않는다.
- 매핑 삭제만 완료하고 개인별 이벤트/사진/본문이 남은 것을 ‘파기 완료’로 표시하지 않는다.
- 법정/분쟁 보존 예외가 실제 필요하면 대상·근거·승인자·만료/재검토 날짜·접근 범위를 지정한다. 일반 분석/수익화로 재사용하지 않는다. 예외 보존 자체도 기본 비활성이다.
- 백업을 삭제 데이터 판매원으로 사용하지 않는다. 보유기간·복원 시 삭제 요청 재적용·새 서비스 노출 전 정리 절차를 둔다. 삭제 재적용 목록도 개인정보 위험이 있어 최소 정보·권한·기간을 정한다.
- 삭제 작업은 중복 실행에 안전하고, 실패를 재시도하며, 작업 중 생성/수정 이벤트와 경합해도 원문이 되살아나지 않게 한다.
- 공개 snapshot 정책을 도입하더라도 snapshot이 개인정보 파기 예외가 되지는 않는다.

새 법정 보유기간을 AI가 임의로 정하지 마라. 목적 미확정 데이터는 장기 저장하지 않으며, 필요한 사람의 승인 전 실제 보관 정책을 연장하지 않는다.

#### S3와 객체 수명주기

S3 영역은 아래 목적별 버킷과 역할 분리를 기본안으로 설계한다. 실제 버킷 생성/정책 변경은 승인 전 실행하지 않는다. 동일 버킷 prefix를 택하면 이름만 나눈 것이 아니라 동등한 IAM 제한을 검증하고 한계를 기록한다.

| 영역 | 저장 대상 | 핵심 통제 |
| --- | --- | --- |
| 운영 미디어 | 실제 서비스 이미지·검증된 파생본 | 비공개 기본, 소유/참여 권한 확인 후 제공, 원본·썸네일·변환본 연결 추적 |
| 백업 | 암호화 DB 덤프·승인된 복구 자료 | 일반 API/분석가 접근 금지, 승인된 보유기간, 격리 복원 후 삭제 재적용 |
| 제한 보존 | 실제 법적 근거와 승인된 범위의 증빙 | 사건/근거/만료 정책별 접근 제한, 분석 전용 금지, 예외 종료 후 파기 |
| 분석 결과 | 승인된 최소 분석 자료·검토된 집계 파일 | restricted와 release 접근 분리, 승인 전 외부 접근 금지, 버전·기한 추적 |

- DB는 소유 관계·객체 키·버전/파생 관계·분류·정책·삭제 작업을 관리하고, 파일은 객체 저장소에 둔다. DB 행 삭제로 객체 추적 정보가 먼저 사라지지 않게 outbox를 같은 트랜잭션에 남긴다.
- 삭제 사용자별 JSON/CSV/사진 묶음을 S3에 영구 아카이브하지 않는다. 얼굴·글자·배경·메타데이터가 남은 사진은 계정 ID를 지워도 익명이라고 판단하지 않는다.
- Block Public Access, TLS, 서버 측 암호화와 필요한 KMS 키 권한, 최소 IAM, 조회/관리 감사, Lifecycle을 목적별로 설계한다. 감사 로그 자체도 개인정보를 최소화한다.
- 버전 관리 버킷의 일반 DELETE는 이전 버전을 남길 수 있다. DeleteMarker만 확인하지 말고 versionId·비현재 버전·파생본·복제 대상·미완료 multipart upload까지 실제 정리 범위를 검증한다. [AWS 객체 버전 삭제 문서](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html)
- 즉시 파기 작업은 명시적 객체 삭제와 확인/재시도를 사용하고 Lifecycle은 기간 만료 및 누락 정리의 보조 수단으로 둔다. Lifecycle 설정 완료를 실제 파기 완료로 기록하지 않는다.
- Object Lock을 사용자 미디어/전체 백업에 무조건 적용하지 않는다. 파기 의무와 충돌할 수 있는 보존 잠금은 근거·대상·기간 승인 후에만 선택한다.
- 실패·403·버전 잠금·복제본 잔존은 미완료 또는 승인된 보존 예외로 명시한다. DB를 지웠다는 이유로 성공 처리하지 않는다. CDN/앱/브라우저 캐시는 회수 가능 범위를 구분하며, 이미 이용자가 내려받은 복사본까지 삭제했다고 주장하지 않는다.
- S3 저장 리전·복제 리전·수탁자/국외 이전 해당 여부를 검토 목록에 넣는다. 암호화와 리전 선택만으로 모든 개인정보 요건이 충족됐다고 말하지 않는다.

### 8. 데이터 가치를 보존하는 분석 파이프라인

외부 판매용 데이터는 개인 기록 덤프가 아니라 카테고리별 실천량·완료율, 기간별 챌린지 참여/완주 경향, 루틴 유지율 같은 집계 결과를 우선한다. 이 표는 구현 후보이지 기존 데이터의 새 목적 이용 승인서가 아니다.

#### 후보 테이블과 책임

- `ProcessingPurpose`: 목적·근거 검토·허용 필드·정책 버전·승인/종료 상태.
- `PolicyVersion`/`ConsentRecord`: 고지/동의 문서 버전과 실제 선택/철회 이력. 기존 사용자 동의를 임의로 만들어 넣지 않는다.
- `RetentionPolicy`: 데이터 분류별 기산점·기간·파기 방식·근거·승인.
- `PurposeSubjectMap`: 꼭 필요한 가명 매핑. 분석가/반출 역할 접근 금지.
- `AnalyticsEvent` 또는 최소 staging 모델: 목적·스키마 버전·보유 만료·멱등 키·허용된 숫자/분류 필드만 포함. 임의 JSON payload로 원문을 복제하지 않는다.
- `AggregateMetric`: 기간 구간·넓은 카테고리·지표·처리 버전. 개인별 행을 넣지 않는다.
- `DatasetRelease`/`ReleaseReview`/`ExportAudit`: 목적·받는 자·출처/버전·검토 결과·승인·접근/반출 이력.
- `ErasureTask`/`ObjectDeletionTask` 또는 동등한 outbox: 삭제·객체 정리 재시도와 감사.

기존 모델/작업 큐로 충족 가능하면 재사용한다. 각 테이블은 실제 기능·유효기간·권한·검증 책임이 있어야 한다.

#### 파이프라인 요구사항

1. 운영 DB 전체 미러링 금지. 수집 시점부터 목적/필드 allowlist를 적용한다.
2. 기본 제외: 이메일·닉네임·핸들·생년월일·IP·기기 ID·토큰·사진·미디어 URL·자유서술 TODO/메모/채팅·신고 본문·정확한 위치.
3. 날짜/시간은 목적에 필요한 단위로 구간화한다. 연령대나 민감한 카테고리도 꼭 필요한지 따로 검토한다.
4. 별도 근거 없는 과거/탈퇴 원문 backfill은 금지한다. 합성 데이터로 파이프라인을 검증하고 실제 수집은 승인된 목적만 활성화한다.
5. 반복 완료/취소·재시도·계정 삭제·늦은 이벤트·수정·복제 이벤트가 통계를 중복 계산하지 않게 한다. 출처와 멱등 추적 키는 필요한 restricted 영역에만 두고 기간을 제한한다.
6. 작은 집단 숨김, 희귀 조합 통합, 기간/분류 일반화, 최소 고유 참여자 수, 기여도 제한을 적용한다. 필요 시 검토된 차등 개인정보보호 같은 추가 기법을 사용한다.
7. 최소 집단 크기를 ‘법적 안전 기준 숫자’로 발명하지 마라. 특정 숫자 하나를 충족했다고 익명이라고 판정하지 않는다.
8. 여러 리포트의 차이·반복 필터링·외부 데이터 결합으로 개인을 추론할 수 있는지도 검토한다. 고객에게 운영 DB 임의 SQL/무제한 필터를 제공하지 않는다.
9. 익명성 검토가 끝나지 않은 결과는 `restricted/unreviewed` 상태로 둔다. 자동 job 완료만으로 ‘익명 승인’ 상태가 되면 안 된다.
10. 반출은 목적·수신자·버전·적정성 검토·필요한 계약/승인 기록이 모두 있어야 가능하다. 기본 OFF이고 테스트용 합성 반출만 허용한다.
11. 원문 삭제 전 익명화를 시도한다는 이유로 파기 의무를 미루지 않는다. 보관·제공의 적법성은 처리 단계별로 확인한다.

현재 10~30명 베타 규모에서는 대부분의 세분화 결과가 소수 집단이 될 수 있다. 외부 판매 가능한 데이터가 반드시 생성된다고 약속하지 마라. 적법한 집계·리포트의 가치 축적이 목표이며, 무제한 원문 축적이 목표가 아니다.

#### 월별 집계와 탈퇴 파기 분리 계약

1. **수집/가공 허용 확인:** 처리 목적·필드·근거·승인·필요한 동의가 확인된 경로만 작동한다. 집계가 가능하다는 이유로 원본 수집 권한이 생기지 않는다.
2. **매일 누적:** 승인된 최소 데이터로 월별 지표를 누적한다. 월 구간은 `Asia/Seoul` 기준 `[월 시작, 다음 월 시작)`을 기본안으로 명시하고, 이벤트 저장 시각과 사용자 시간대 의미를 분리한다.
3. **연령대 일반화:** 연령대가 필요한 승인 지표에 한해서 집계 대상 활동 당시 만 나이 기준 10년 구간을 사용한다. 기존 생년월일을 새 분석용으로 수집/복사하지 않는다. 활동 당시 연령을 신뢰성 있게 계산할 수 없으면 ‘알 수 없음’으로 처리하며 현재 나이를 과거 활동에 소급하지 않는다. 생일로 구간이 바뀐 사용자의 중복 인원 합산 문제를 정의하고, 나이 추론이 필요 없는 지표는 연령대 없이 집계한다.
4. **제한된 중간 상태:** 월별 숫자라도 작은 집단·개인별 키·정확한 기여 추적이 남아 있으면 `analytics_restricted`에서 개인정보 수준으로 관리한다. 매일 갱신한 세분화 결과를 공개해 차분으로 한 사람을 추론할 수 있게 하지 않는다.
5. **탈퇴 독립 처리:** 접근 차단과 파기 절차를 시작하고 월말을 기다리지 않는다. 미집계분을 확보하려고 원문을 별도 저장하거나 파기 작업이 analytics 성공을 기다리게 하지 않는다. 이미 적법하게 만들어졌고 익명성 검토를 통과한 집계와 삭제 대상 개인별 중간 자료를 구분한다.
6. **재유입 차단:** 삭제 중/이후의 지연 이벤트·재시도·백필·복원으로 개인 자료를 다시 적재하지 않는다. 이를 위한 최소 삭제 재적용/중복 방지 기록도 별도 보유정책과 권한을 갖고, 영구 사용자 해시 블랙리스트로 대체하지 않는다.
7. **월말 검토:** 중복·완료 취소·수정·늦은 이벤트 처리, 소수 집단 병합/비공개, 희귀 조합·교차 리포트 차분 위험을 검증한다. 월말 도달은 익명 승인 조건이 아니다. 지연 반영 마감과 결과 수정 정책은 문서로 정의한다.
8. **버전 확정/제공:** 검토된 월별 결과만 버전 확정한다. 외부 제공은 별도 승인 게이트를 통과해야 한다. 이전 버전과의 차이로 재식별이 가능한 수정본을 자동 공개하지 않는다.

9월 8일 탈퇴 사례를 테스트 데이터로 문서화해라: 9월 활동의 기존 승인 익명 집계는 필요한 검토 후 유지 가능하지만, 개인별 분석 중간 행·계정·파기 대상 사진은 월말과 독립적으로 정리한다. 미집계분 유실을 피한다는 이유로 원문을 잡아두지 않는다. 삭제 때문에 일부 지표의 정확한 재계산이 불가능하면 지표 정의·품질 상태로 드러내고 원문을 몰래 보관하지 않는다.

통계 후보는 ‘활동 월 × 연령대(필요할 때만) × 넓은 표준 카테고리’의 건수·완료율부터 시작한다. 사용자 정의 카테고리명도 자유서술일 수 있으므로 그대로 반출하지 않는다. 분자·분모·고유 참여자 산정·개인 기여 상한을 지표별로 정의하며, 작은 베타에서 구간을 합치거나 연령 차원을 빼는 결과를 허용한다.

후보 구현은 `AggregationJob`/`MonthlyAggregate`/`AggregateReview` 또는 기존 동등 모델을 재사용한다. `기간 + 목적 + 지표 + 구간 + 처리 버전`에 대한 멱등성과 동시 실행 잠금을 제공한다. 개인정보 중간 자료와 확정 익명 결과는 접근·수명 정책을 분리한다. 개인정보 파기 큐와 통계 큐를 분리하고 파기 지연/실패를 우선 경보한다.

### 9. 기존 보안 감사도 함께 해결해라

`2026-09-08-security-audit-and-plan.md`의 SEC ID를 진행표에 연결한다.

우선 구현:

- SEC-02: 소프트 삭제 항목이 그룹 전체 복제로 되살아나지 않게 공개/복제 조건 통일.
- SEC-03: 현재 DB role을 권한 판단에 반영하고 관리자 역할 변경 시 기존 세션 권한 회수.
- SEC-04/05: 개인 미디어/인증 URL SW 캐시 제외, 계정 전환 정리, 적절한 캐시/서명 만료, 원본 삭제 실패 추적.
- SEC-01: 운영 HTTP/비보안 쿠키 fail-closed와 개발 예외 분리.
- SEC-06: seed bootstrap·비밀번호 변경 세션 폐기·민감 작업 재인증. 관리자 MFA 수단은 권고안을 제시하고 실제 운영 등록/복구 정책은 사용자 승인을 받아라.
- SEC-07/08: CSRF 정책, IP+계정 제한, quota 원자 예약, 처리 잠금, Socket 입력/빈도 제한.
- SEC-09/11: 웹 CSP/프레이밍, 민감 조회 감사·로그 마스킹. Google 로그인/Next 렌더링을 깨지 않게 단계 적용.
- SEC-10: 공개 원본/snapshot 정책은 선택지를 설명하고 승인 전 임의로 개인정보 공개 범위를 바꾸지 않는다.
- SEC-12/13/14: DB/S3/백업 역할 분리, secret/이미지/Android 검사, 격리 통합 테스트.

실제 TLS/IAM/방화벽/학교 Docker 권한은 코드만으로 해결됐다고 표시하지 마라. 운영 설정을 바꿔야 하면 실행 전 별도 승인을 요청한다.

### 10. 테스트와 완료 조건

최소 테스트:

- 빈 DB 전체 migration, 기존 데이터 포함 업그레이드, rollback 가능한 단계 복원, `_prisma_migrations` 일관성.
- 원래 PK/관계/행 수·대표 내용이 유지되며 로그인·Google 로그인·TODO·게시·복제·채팅·챌린지가 동작.
- 실제 DB role별 허용/거부 SELECT/JOIN/INSERT/UPDATE/DELETE/DDL. 분석·반출 역할은 identity/매핑/원문을 읽을 수 없음.
- 탈퇴/철회/기간 만료의 DB·객체·캐시·분석 데이터 파기, 실패 재시도, 중복 작업, 백업 복원 후 삭제 재적용.
- 익명 집계 출력에 직접 식별자·안정적 개인 키·원문·정확한 시각이 남지 않음. 작은 집단/차분 조회 반출 거부.
- 목적/동의/정책 승인 없는 수집 및 반출 차단. 과거 사용자에게 승인 레코드가 자동 생성되지 않음.
- 삭제 TODO 그룹 복제 차단, 역할 강등 토큰, 미디어 소유권·동시 처리·삭제 실패·CSRF·관리자 재인증 회귀.
- 실제 PostgreSQL/Redis/MinIO/Mailpit의 합성 계정 A/B/관리자/모더레이터로 HTTP 및 필요한 Socket 테스트.
- L0~L3별 허용/거부와 필드 누출, L3 운영자도 모든 개인 대화/인증 정보를 읽지 못하는 목적·객체 권한 테스트.
- S3 버전 관리 ON/OFF의 파생본/과거 버전 삭제, 삭제 표시만 존재하는 경우 실패 판정, 권한 거부/잠금/복제본 잔존, Lifecycle과 실제 파기 완료 구분. MinIO 검증과 AWS 고유 동작 검증을 구분하고 실제 AWS 미검증 항목은 운영 승인 대기로 남김.
- 월 경계·연도 경계·사용자 시간대·연령대 변경·나이 미상·늦은 이벤트·완료 취소·재시도·동시 집계의 정확성.
- 9월 8일 탈퇴 시 월말까지 기다리지 않는 파기, 집계 서버 장애 중에도 파기 진행, 탈퇴와 집계 경합·지연 outbox·백필/복원에서 개인정보 재유입 방지.
- 제한된 집계의 개인별 자료 파기, 이미 승인된 익명 집계의 보존 구분, 최소 고유 참여자 검증과 여러 버전 차분을 통한 재식별 방지.

검사 명령은 현재 저장소 스크립트를 확인해 `npm run lint`, `npm test`, `npm run build`, 운영 의존성 감사와 새 DB/보안 테스트를 수행한다. 기존 API 테스트 54개 통과·DB E2E 1개 skip은 지난 결과이지 이번 구현의 검증 결과가 아니다.

모의 객체 테스트만으로 권한 분리·DB migration·객체 파기를 검증 완료라고 보고하지 마라. 실제 DB 테스트가 없으면 해당 항목은 미검증으로 남긴다. migration 성공만으로 개인정보 적법성·익명성 검토까지 승인됐다고 말하지 마라.

### 11. 구현 단계와 산출물

단계별로 작은 변경과 검증을 남겨라.

1. 인벤토리·L0~L3 권한/목적/보유 행렬·ADR·승인 필요 결정 목록. 익명/가명과 법적 민감정보 분류를 별도 기록.
2. 치명적 기존 보안 결함의 독립 수정.
3. 호환성 검증 후 다중 스키마/역할 및 안전한 데이터 이전 구현.
4. 식별/프로필 분리, 탈퇴 파기 outbox·S3 영역/역할·버전/파생 객체 삭제·백업 복원 재삭제 구현. 분석 작업과 독립적인 파기 경로를 먼저 검증.
5. 승인 게이트가 있는 일별 실행/월별 누적·연령대 일반화·월말 검토/버전 확정·반출 기반을 합성 데이터로 구현. 탈퇴 시 집계하지 못해도 파기가 진행되는 경합 테스트 포함.
6. 남은 보안 강화·전수 회귀·운영 적용 런북. 구현 완료/실환경 검증/법률·정책 승인/운영 반영을 별도 완료 조건으로 보고.

### 12. 금지 사항과 최종 보고

- 현 단계에서 운영 DB 이전·삭제·권한 변경, 실제 사용자 데이터 새 목적 적재/판매/외부 전송, 서버 포트/다른 프로젝트 변경은 하지 않는다.
- Git reset/강제 push/무관한 변경 되돌리기, 별도 요청 없는 commit/push는 하지 않는다.
- 시크릿·사용자 원문·백업 내용을 로그나 최종 답변에 출력하지 않는다.
- ‘법에 맞춰 최대한 보관’을 ‘모든 탈퇴 원문을 가명화해서 무기한 보관’으로 해석하지 않는다.
- 분석 수집/반출을 법적 검토 전 기본 ON으로 만들지 않는다.
- 한 DB를 여러 스키마로 나누거나 FK를 없앴다는 이유만으로 익명화·완전 격리·보안 완료를 주장하지 않는다.

최종 답변에는 실제 변경 구조, 데이터 보존 검증, 해결한 SEC ID, 실행한 테스트/skip, 적용하지 않은 운영 migration, 정책·MFA·법률·인프라 승인 대기, 남은 위험을 구분해 적어라.
